Doorman — C4 改善案アーキテクチャ

現行（v26 相当）の構造課題を踏まえた目標形の C4モデル。

中心となる構造変更は「単一実行権限 + 永続キュー」「SQLite を真実の源とするイベント射影」「共通パイプラインエンジン + チャンネル戦略」「LLM クライアント seam」「明示的なターゲット状態機械」。

これは提案であり、現行実装ではありません。現行構造は docs/c4-architecture.html を参照。各図に「現行との差分」を併記しています。

改善の狙い（なぜ作り直すか）

現行は本番インシデントごとの信頼性パッチ（v4→v26）の積層で、host_role のプライマリホスト・ゲーティング、run_supervisor の stall 検知＆再起動、「再起動で冪等」回復、detached プロセス監視、ファイルベース状態——これらは本来「1つの永続キュー + 単一実行権限 + 共有状態ストア」という構造プリミティブの手作り代替です。この目標形は、それらを1つの枯れたパターンへ畳み込み、二重送信を規約ではなく構造として封じます。

外部関係は現行とほぼ同じ。違いは境界を明確化した点：OpenClaw + Claude を一貫して外部プラットフォームとして扱い、reCAPTCHA/Turnstile を「解かず回避する相手」として明示する。

現行との差分（主要 5 点）:
  1. 永続キュー + 単一 Worker を新設 → run_supervisor の stall/再起動・「再起動で冪等」・detached監視を吸収。
  2. SQLite を真実の源に → JSONL は監査イベントログに格下げ（射影元として維持）。「2台が食い違う」系を構造的に排除。
  3. パイプラインエンジン + チャンネル戦略 → jp-form/linkedin の run.py 二重実装を解消。
  4. LLMクライアント seam → ブラウザと同様に推論も抽象化。oc_infer subprocess は1実装に。
  5. 送信ドライバ（v24ループ）を全チャンネル共通の唯一のドライバへ昇格。レゾルバは型付きアクション化。

Deployment — 多ホストと送信権限

現行で最重要なのに図に出ていなかった軸。送信できるのは Worker のリースを保持する1台だけ。dev機は worker を起動しないので、CLIを叩いても・Slackが誤配信しても、構造的に送信できない。

現行との差分: 「devは送信を拒否する」procedural guard（host_role）から、「worker リースを持つ1台しか送れない」structural guard へ。watchdog の stdlib-only 独立稼働（venv破損耐性）は維持。

Dynamic — ターゲットのライフサイクル状態機械

現行では複数 JSONL に暗黙分散していた状態を、明示的な状態機械として SQLite に集約。各 blocked は理由つきで、レゾルバの型付きアクションに対応する。

stateDiagram-v2
    [*] --> queued
    queued --> enriched : enrich
    enriched --> drafted : LLM draft
    drafted --> awaiting_approval : preview
    awaiting_approval --> sending : approve / auto
    awaiting_approval --> skipped : reject
    sending --> sent : verify OK
    sending --> blocked : captcha / submit-not-found / content-rejected
    blocked --> sending : typed resolve action
    blocked --> skipped : unviable domain learned
    sent --> [*]
    skipped --> [*]
現行との差分: sent_history/skip_history/events/resolve_queue に散っていた状態を1つの遷移モデルへ。blocked → sending は「同じ検出の再試行」ではなく型付き解決アクションで起こす。

移行の順序（インクリメンタル）

段階内容得られるもの
1SQLite を「送信済み判定」の真実の源に（JSONL から射影）多ホストの食い違い解消・dedup の信頼化
2SQLite-backed キュー + 単一 worker を導入、run_job をその上に再実装run_supervisor/再起動冪等を吸収、送信権限が構造化
36フェーズを engine に抽出、jp-form/linkedin を戦略プラグイン化二重実装の解消・パッチ適用面が半減
4LLMクライアント seam を切る（CLI 実装を温存しつつ API 実装追加）テスト容易性・構造化出力・起動コスト減
5送信ドライバ統一 + レゾルバ型付きアクション送信信頼性の一元化・回復の原則化
変えない方がよい資産: 決定論と LLM の分離 / append-only イベントログ（射影元として残す）/ ブラウザのアダプタ seam（即ロールバック）/ watchdog の stdlib-only 独立性。目標形はこれらを壊さず、その上に構造プリミティブを足す方針です。
