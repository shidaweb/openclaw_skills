# Doorman 外販アーキテクチャ（v6）— オンデバイス × 公式API優先 × 合法的 reCAPTCHA

> 本書はエンジニアリング設計の提案であり、法的助言ではない。特定電子メール法 / 個人情報保護法
> （APPI）/ 各サイトの利用規約（ToS）/ reCAPTCHA 規約の最終判断は法務レビューを前提とする。

## 0. 結論（先に）— 前提を2点更新

- **更新1**: フォームでは**実際に reCAPTCHA が出る**。よってフォーム営業（jp_form）に限り
  reCAPTCHA 回避を一段強化する（§3.5 ディープダイブ）。他チャネルは CAPTCHA 非対象。
- **更新2**: **オペレーターは基本いない＝完全自律前提**。人手フォールバックには依存しない。

この前提だと、技術的・法的に成立する設計は一つに収束する:

- **勝てるのは「出させない（回避）」だけ。** 完全自律で“出た可視チャレンジを突破”する方法は、
  確実性・合法性・ToS適合のいずれも満たさない（reCAPTCHA はまさに自動フォーム送信を止める仕組み）。
  よって本設計は **回避に全力を注ぎ、出てしまった対象は「突破」せず別経路にルーティング**する。
- **回避の最大の武器はオンデバイス**: 顧客端末の実ブラウザ・実 residential IP・永続プロファイルから
  低volumeで送るため、v3/Enterprise の評価スコアが自然に健全に保たれる。偽装ではなく「実際に正当な
  発信者の実ブラウザである」ことがそのままスコアになる（これが回避の効く根拠であり、高volumeスパムを
  不可視化する手段ではない）。
- **出てしまったら（人手なし）**: 代替チャネル（公式API/メール/LinkedIn）へ fallback → 好条件で再試行
  → それでも不可なら skip＋記録。**機械での自動回答・ソルバーファーム・fingerprint 偽装は採用しない**
  （ToS違反・arms race・外販プロダクトを悪用ツールに変えるため）。
- **正直なカバレッジ（営業・契約のため重要）**: reCAPTCHA 非搭載 / v3・invisible のフォームは自律送信で
  カバーできる。一方 v2 を既定で可視表示するサイトや厳格な Enterprise は、スコアに関係なく毎回
  チャレンジするため**自律フォーム送信は物理的に不可能**。これらは迂回・レポートに回す。SLA は
  「自律カバー率＋迂回率」で表現し、「全フォーム100%自律送信」とは謳わない。

## 2. Channel Resolver（公式API優先の中核）

ターゲット 1 件ごとに「最も正当で摩擦の小さい合法チャネル」を選ぶルーター。`Pull/Enrich` の段で
判定し、選定理由を監査ログに残す。

| 優先 | チャネル | 条件 | CAPTCHA | 規約適合性 |
|---|---|---|---|---|
| 1 | **official_api** | 相手が問い合わせAPI/パートナー連携を提供 | 無 | 最良（公式手段） |
| 2 | **email** | 公開の B2B 問い合わせメール＋送信が適法 | 無 | 良（※特定電子メール法/オプトアウト要件を満たす範囲） |
| 3 | **jp_form** | 公開Webフォームのみ。ToS が自動送信を禁じていない | v3 警戒/v2 出る | 可（回避強化§3.5＋遭遇時は迂回/skip） |
| 4 | **linkedin** | 相手が LinkedIn 上にいる | 無（公式InMail） | 良（公式製品の範囲） |
| 5 | **skip** | 適法チャネルが無い / 「B2B 勧誘お断り」シグナル | — | 送らない |

ルーターは「相手の ToS / robots / 明示の勧誘拒否」を検出したら**自動的に格下げ or skip**する。
これにより、そもそも CAPTCHA に当たるフォーム送信の比率を下げる。

Channel Adapter は共通インターフェース（`resolve → enrich → draft → send → verify → log`）で実装し、
既存の `jp_form` / `linkedin` をこの抽象に寄せる。`official_api` / `email` を新規アダプタとして追加。

## 3. reCAPTCHA 方針レイヤー（完全自律・人手なし）

階層ポリシー。**回避 → 検知 → 自律ルーティング（突破しない）→ 保留/skip → 禁止**。

1. **Avoid（出させない）＝ 主戦場**: §3.5 のフォーム強化策。warmup＋実ブラウザ＋実IP＋人間的ペースで
   v3/Enterprise スコアを健全に保ち、そもそもチャレンジを出させない。
2. **Detect（分類）**: v2 visible / v3 invisible / hCaptcha / none を enrich で判定。さらに「このドメインは
   毎回 v2 を出す」を学習し、回避不能ドメインを早期に切り分ける（§3.5-D）。
3. **Autonomous routing（突破しない・人を待たない）**: 可視チャレンジを検出したら**解こうとしない**。
   - **代替チャネル**へ即 fallback（official_api / email / linkedin）。
   - 無ければ**好条件で再試行**（warm session・off-peak・追加warmup、指数backoff、上限N回）。
4. **Defer / skip**: 再試行も不可なら skip＋記録（autonomous の既定動作、実装済）。
   「CAPTCHAブロック」レポートへ集約してクライアントへ可視化。
5. **Never（禁止・明文化）**: 第三者自動ソルバー、音声/画像ML による自動回答、fingerprint 偽装/stealth に
   よる automation の秘匿、residential proxy rotation による IP ロンダリング、token 横流し。
   **プロダクト原則として不採用**（ToS違反・arms race・悪用転用リスク）。

> 補足: ToS が「自動フォーム送信そのもの」を禁じるサイトは、スコアが高くても Channel Resolver が
> skip する。CAPTCHA の可否と ToS の可否は別問題として両方判定する。

## 3.5. フォーム reCAPTCHA 回避 ディープダイブ（完全自律前提・jp_form 限定）

「人手なしで、どうやって遭遇させず、出ても止まらないか」を一段深く。結論は **遭遇率を下げる工学に
全振りし、遭遇したら突破せず迂回する**。この節の強化は **フォーム営業チャネルにのみ**適用する。

### A. なぜ「出た後に自律で突破」を設計しないか（正直な技術判断）

reCAPTCHA は自動フォーム送信を止めるために存在する。可視チャレンジを**人手なしで・確実に・合法に・
ToS適合で**解く方法は存在しない。音声/画像のML自動回答もソルバーファームも、Google の規約違反であり
継続的な arms race（向こうが対策し続ける）で、外販プロダクトの致命的リスクになる。よって本設計は
チャレンジを**パズルとして解かず、ルーティングのシグナルとして扱う**。

### B. v3/Enterprise スコアモデル（出させないための原理）

v3/Enterprise は送信のたびに 0.0–1.0 のリスクスコアを返し、**サイト側が閾値**を持つ。低いと
ブロック/チャレンジ。スコアを**下げる**主因＝避けるべきもの:

- automation fingerprint: `navigator.webdriver=true`、headless UA、CDP 痕跡、plugin/フォント/WebGL の欠落
- IP 評価: データセンターIP・VPN・共有プロキシ
- エンゲージメント皆無: cookie/履歴なし、初訪問で即送信、サイト滞在ゼロ
- 非人間的入力: 瞬間入力、マウス移動なし、毎回同一タイミング
- バースト送信: 同一ドメインへ短時間に連続

### C. 回避レバー（オンデバイスの強み × 低volume・正当が前提）

**偽装ではなく、「自分が実際にそうである＝正当な低volume発信者の実ブラウザ」として振る舞う**。

1. **実ブラウザを使う（最重要）**: ephemeral な headless ではなく、顧客端末の**実 Chrome ＋永続
   user-data-dir** に CDP 接続して駆動。automation artifact を「隠す」のではなく**最初から出さない**。
2. **実 residential IP をそのまま使う**: オンデバイスなので proxy rotation 不要。IP 評価が自然に良い。
3. **Warmup 強化**（既存 `warmup.py` を深掘り）: ルートドメイン着地 → cookie 受容 → 数秒 dwell →
   スクロール → 人間的マウス曲線 → フォームへ遷移。サイトエンゲージメントを蓄積してからフォーム操作。
4. **人間的入力モデル**: キー間隔のばらつき、フィールドへのマウス移動、focus/blur、現実的な総入力時間、
   妥当な範囲でのフィールド入力順ランダム化。v3 の interaction シグナルを健全化。
5. **Cookie 永続化**: Google `_GRECAPTCHA` とサイト cookie を**端末・brief 単位で保持**。再訪・cookie
   持ちの訪問者は高スコアになりやすい。
6. **レート/時間帯**: ドメイン別の低頻度＋jitter＋営業時間送信。バースト禁止。**1端末＝一貫した1
   アイデンティティ**（アイデンティティを回さない）。
7. **v2 invisible / checkbox**: スコアが高ければ checkbox クリックのみで no-challenge トークンが発行
   される場合がある。ただし**画像チャレンジが表示されたら C の領域を超える**ので D/E へ。

> これらは「高volumeスパムを不可視化する手段」ではない。低volume・正当だからスコアが保てる。

### D. 自己調整フィードバックループ（回避を“学習”させる）

- ドメイン/フォームテンプレ別に **CAPTCHA 遭遇率・送信成功率**を events に記録。
- あるドメインが回避策後も**常に可視チャレンジ**を出す → `form-channel unviable` とマークし、以後は
  自動で代替チャネル or skip（無駄打ちと低スコア累積を防ぐ）。
- warmup 秒数・入力ペース等のパラメータを成功率で自動チューニング（簡易 bandit）。

### E. Residual ポリシー（出た／通らない時の完全自律動作＝突破の代わり）

1. **チャネル fallback**: その対象を official_api → email → linkedin で再 resolve（§2）。
2. **Defer & retry**: より良い条件（warm セッション・off-peak・追加 warmup）で再キュー。指数 backoff、
   上限 N 回。条件を変えると通ることがある（スコアは状態依存のため）。
3. **Skip + log**（実装済 autonomous）＋「CAPTCHAブロック」レポートに集約。
4. **（任意 opt-in）非常勤の人手バッチ**: クライアント自身が稀に非同期でまとめて片付ける任意キュー。
   ソルバーファームではない。既定オフ。「オペレーターはいない」前提なら未使用でよい。

### F. やらないこと（明文化）

ソルバーファーム / 音声・画像ML自動回答 / fingerprint 偽装・stealth で automation を隠す /
residential proxy rotation で IP をロンダリング / token 横流し。**いずれも不採用**。

### G. 正直なカバレッジ表現（営業・SLA）

「reCAPTCHA 非搭載 or v3・invisible のフォーム＝自律送信。v2 を常時可視表示・厳格 Enterprise＝迂回/
レポート」。SLA は**自律カバー率＋迂回率**で表現し、全フォーム100%自律送信は約束しない。

## 4. オンデバイス配備（外販の形）

「顧客端末に OpenClaw ＋ツール一式をインストール」を前提に、配備・運用・更新を設計する。

- **インストーラ**: OpenClaw gateway ＋ skills ＋ `.venv` ＋ Playwright ＋ watchdog(launchd/Task Scheduler)
  をワンショット導入。`scripts/install-*.sh` を外販インストーラに昇格。
- **アイデンティティ**: 送信は顧客の実ブラウザプロファイル（実IP・実Cookie）。匿名プロキシや
  データセンターIPは使わない（正当性 by construction の前提を崩さない）。
- **ローカル状態**: briefs / sent・skip history / 監査ログ / リードPII はすべて端末内。
- **ライセンス**: 端末ごとの entitlement チェック（オフライン猶予付き）。
- **更新**: skill / prompt / channel adapter は**署名付き**でベンダーから配信。顧客データは送らない。
- **テレメトリ**: 既定オフ。opt-in 時のみ匿名・集計値（送信成功率・CAPTCHA遭遇率など）。本文・PII は対象外。
- **自己復旧**: 既存の watchdog（死活/hung/切断の自動再起動）＋ run 冪等再開を標準同梱。

利点: ベンダーが顧客のリード PII を預からない → APPI 上の委託/第三者提供・越境移転の論点を最小化でき、
外販の契約（DPA）と審査が軽くなる。

## 5. Compliance Guardrails（外販を“可能”にする仕組み）

プロダクトが**違法・規約違反な使い方をしづらい**構造を持つことが、そのまま外販可能性になる。

- **送信者の正当性**: 顧客が検証済みの送信者アイデンティティを設定（誰が送るかが明確）。
- **法的根拠の明示**: B2B の正当利益／公開された企業窓口への営業、という前提を brief に記録。
- **抑止・オプトアウト**: グローバル Do-Not-Contact、配信停止/「お断り」の自動尊重、ドメイン別頻度上限。
- **レート＆礼節**: ドメイン別スロットル、営業時間内送信、フォーム経路は robots を尊重。
- **ToS 判定**: 自動送信禁止の明示があるサイトは Channel Resolver が skip。
- **監査証跡**: send / skip / CAPTCHA迂回・再試行 を append-only で不可変ログ化（既存 events/history を拡張）。
  顧客自身のコンプライアンス記録として提出可能に。
- **承認ゲート**: 既存の事前一括承認（autonomous）＋ supervised を選択可能。autonomous は顧客が
  「正当性アテステーション」に同意した上で opt-in。
- **PII最小化 / 秘匿**: trace の sender PII redaction（テスト済不変項 `redact_sender`）を全アダプタへ適用。

## 6. 法令・規約の整理（要法務レビュー）

- **特定電子メール法**: email チャネルを使う場合に関与。B2B 公開アドレスへの送信・オプトアウト導線・
  送信者表示などの要件を email アダプタに組み込む（フォーム送信とは別ルール）。
- **個人情報保護法（APPI）**: 送信先の担当者情報は個人情報になり得る。取得経路の適法性・利用目的・
  オプトアウト対応を設計に内蔵。PII を端末に留める構成で委託/越境の論点を縮小。
- **各サイト ToS**: 自動送信を禁じるサイトの尊重。Resolver の skip 判定に反映。
- **reCAPTCHA 規約**: 機械的な自動回答・検知回避ハックを行わない（スコア健全化による回避＋遭遇時の
  迂回のみ）方針を明文化。
- **越境・モデル**: 下書き生成でモデルAPIを使う際は無保持（zero-retention）ティアを選び、DPA に明記。

## 8. 段階導入ロードマップ

1. **Phase 1 — 抽象化**: Channel Adapter 共通IFを切り、既存 jp_form / linkedin を載せ替え（挙動不変）。
2. **Phase 2 — 公式チャネル**: `email` と `official_api` アダプタを追加し、Resolver を「公式優先」に。
3. **Phase 3 — コンプライアンス内蔵**: suppression / rate / ToS判定 / 監査ログを Guardrails として中央化。
4. **Phase 4 — フォーム reCAPTCHA 回避エンジン**: 実ブラウザCDP＋人間的入力＋cookie永続＋遭遇率学習で
   v3スコアを最大化し、遭遇したら代替チャネル/再試行/skip へ自律ルーティング（§3.5）。
5. **Phase 5 — 配備プロダクト化**: インストーラ / ライセンス / 署名付き更新 / opt-in テレメトリ。
6. **Phase 6 — 監査・契約**: 顧客提出用コンプライアンスレポート、DPA テンプレ、法務レビュー。

## 9. やらないこと（非対象 / リスク源の排除）

- ❌ 第三者自動ソルバー（2captcha 等）・画像認識による CAPTCHA 機械回答
- ❌ データセンターIP / 匿名プロキシ / フィンガープリント偽装による検知回避
- ❌ 顧客リード PII のベンダー集中保持・越境移転（端末内に留める）
- ❌ ToS が自動送信を明示的に禁じるサイトへの送信
- ❌ オプトアウト・お断りシグナルの無視

```
正当性は構造で担保する（legitimacy by construction）。
評価スコアは健全に保ち、出てしまったチャレンジは突破せず迂回し、公式チャネルを優先する。
破るのではなく、破る必要のない経路を選ぶ。
```
